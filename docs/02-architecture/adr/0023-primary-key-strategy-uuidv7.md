# ADR-0023: Primary key strategy — UUIDv7 ids and composite tenant keys

- **Status:** Proposed
- **Date:** 2026-10-16
- **Deciders:** Data architect, Solution architect
- **Related:** ADR-0020, ADR-0022, ADR-0033 (migration key maps), ADR-0036 (dedicated tier); [DESIGN.md](../../../database/postgresql/DESIGN.md) §4.1; DDL `sys.uuid_v7()`

## Context

Ids appear in APIs, events (`event_id`, aggregate ids), outbox payloads written before commit, bulk imports (opening-balance import, ADR-0037), and tenant moves between pool clusters and the dedicated tier. Large tables (punches, result lines, audit) need insert-friendly indexes. RLS and composite FKs both benefit from `tenant_id` in keys.

## Decision

1. Surrogate key `id uuid`, **UUIDv7** (time-ordered), generated by the application. The column default `sys.uuid_v7()` is the SQL fallback; on PostgreSQL 18 it is replaced by the built-in `uuidv7()`.
2. `tenant_id uuid` (UUIDv7). The sentinel `00000000-0000-0000-0000-000000000000` marks global rows in global + tenant tables (ADR-0035).
3. Tenant-owned tables use **PK `(tenant_id, id)`**. Partitioned tables append the partition key (`(tenant_id, id, occurred_at)`).
4. APIs and events expose `id` only; it is globally unique.
5. Business keys (`employee_no`, `code`, `contract_no`) are separate `UNIQUE (tenant_id, …)` constraints and are editable.
6. `bigint` is used only where a gap-free order is the point: `audit_event.chain_seq`, `legal_param_pack.pack_version`, `override_version`.

## Alternatives considered

| Option | Why not |
|---|---|
| `bigint` identity | Sequences are per database, so ids collide when a tenant moves between clusters or into the dedicated tier. They are guessable (enumeration), cannot be generated before insert for the outbox and idempotent imports, and need a hi/lo dance in Hibernate batching. |
| UUIDv4 | Random inserts fragment B-tree indexes on high-volume tables (punches, result lines), with measurable write amplification. |
| ULID / Snowflake (bigint) | ULID needs a text or custom type. Snowflake needs worker-id coordination. UUIDv7 is standard (RFC 9562) and native in PG18. |
| PK `(id)` alone with `tenant_id` as a plain column | No composite FKs, so a cross-tenant parent reference becomes possible, and tenant-leading index locality is lost. |

## Consequences

- \+ Ids are mergeable and movable across clusters, safe to expose, and known before insert.
- \+ Composite FKs make cross-tenant references impossible.
- − Keys are 32 bytes on tenant tables versus 8 for bigint, about 10–15 % more index space on the largest tables. Accepted.
- − UUIDv7 embeds the creation time (millisecond). It is not a secret, but it is not to be used as a business date.
