## 1. Method

1. **Inventory.** I read every §7 Consumes/Provides row in the six BRDs (Core 21/25, People 28/34, T&A 23/16, Payroll 33/18, Recruitment 28/16, SaaS 14/16, so 272 interface rows in total) and every §10 open question (Core 10, People 11, T&A 11, Payroll 11, Recruitment 8, SaaS 11).
2. **Pairing.** I matched each Consumes row with a Provides row by data object, not by name. A row with no counterpart is an **orphan** (§4). Where the counterpart exists but differs in name, payload, timing or owner, I raised a **contract mismatch**.
3. **Overlap scan.** I compared §1 scope, §3 processes, §4 requirements and §6 entities across modules to find the same capability or entity specified twice (**scope overlap / ownership conflict**). I also listed VN HRM capabilities that no BRD covers (**scope holes**, §8).
4. **Seed verification.** I checked each of the 18 PM seed items against the text. 15 are confirmed, 2 are confirmed with corrections (holiday calendar: only Payroll is in doubt; business trips: the priorities differ too), and 1 is partly rejected (settlement deadline wording is consistent; the real gap is elsewhere, see GAP-040). The seed items map to 23 register entries. On top of those, 47 more gaps were found.
5. **Rating.** **Impact:** H = wrong pay or tax, legal exposure, or a cross-module rework; M = a feature defect or duplicate build; L = cosmetic or late-phase. **Blocks MVP = Y** means the decision must be closed before SRS sign-off for an MVP module (charter §6: Core, People, T&A basic, Payroll, ESS, onboarding; the original "Oracle migration" item is replaced by the opening-balance import, D-09 (v1.1)). **Status** (v1.1): *Resolved (ID)* = closed by the named decision-log entry; *Open* = still needs the decision owner.

## 7. Period-close sequence (T&A ↔ Payroll ↔ People) — v1.1 with close hold

(v1.1, X-03) This section is rewritten around the solution architect's **close hold** (ADR-0019, architecture-overview §7.4.2): when Payroll *submits* a run it holds the exact Attendance Result version it calculated on; approval then locks that version, and rejection or rollback releases it. This replaces v0.1 step 9 ("T&A rejects the lock and Payroll's approval is rolled back") and removes the GAP-027 deadlock. Applied in T&A BR-ATT-073/079/087/088 and Payroll BR-PAY-071/082–084.

### 7.1 Unified states

| Object | States | Meaning |
|---|---|---|
| **Attendance period** (T&A, per LE × pay group) | `OPEN` → `IN_REVIEW` → `CLOSED` → `LOCKED`. Reverse paths: `CLOSED → OPEN` (re-open, **only when no hold is active**); `LOCKED → CLOSED` (**only** on payroll unlock) | `CLOSED` = a versioned Attendance Result is published. A `CLOSED` period with an active hold is called *held*: it cannot re-open or change in place. `LOCKED` = the held version was consumed by an **APPROVED** payroll run; frozen, and later changes become retro deltas. |
| **Close hold** (T&A, per period × result version × run) — *new v1.1* | `ACTIVE` → `CONSUMED` (on lock) or `RELEASED` (reason `REJECTED` / `WITHDRAWN` / `CANCELLED` / `REOPEN_REQUESTED` / `UNLOCKED`) | Acquired by Payroll at submit through a synchronous, idempotent T&A API. Never expires by time; only Payroll actions release it. "Held" is a condition of `CLOSED`, not a fifth period state. |
| **Payroll run** (Payroll) | `DRAFT` → `CALCULATED` → `SUBMITTED` → `APPROVED` → `PAID` → `CLOSED`; side states `REJECTED` (→ `DRAFT`), `UNLOCKED` (→ `DRAFT`), `REVERSED`; `SUBMITTED → CALCULATED` on withdrawal or T&A release request (stale flag) | `APPROVED` replaces BR-PAY-071's separate "Locked": approved runs are read-only. The word "Locked" is reserved for T&A periods. A run holds its attendance versions exactly while it is `SUBMITTED`, until the lock consumes the hold on `APPROVED`. |
| **Pay period** (Payroll) | `OPEN` → `INPUT_CUTOFF` → `CLOSED` | `INPUT_CUTOFF` is the People/variable-input watermark. People itself has **no period state** (GAP-064). |
| **Calculation mode** | `PROVISIONAL` / `FINAL` | Calculation is `FINAL` only when every in-scope attendance period is `CLOSED` and its version is recorded. |

**Protocol invariants (v1.1).** (1) Every message carries `(tenant, legal_entity, pay_group, period, result_version, run_id)`; hold, release, lock and unlock are idempotent on `run_id + result_version`. (2) A run can be `SUBMITTED` only if it holds the current version of every in-scope period; if T&A is unavailable or refuses, the submit fails (no orphan holds). (3) A held period never re-opens and never changes in place. (4) Therefore the lock on `APPROVED` cannot fail and **no approval is ever rolled back**. (5) `LOCKED → CLOSED` happens only through unlock; reversal never touches T&A. (6) A nightly reconciliation job compares run, hold and period states for all tenants and alerts on mismatches (e.g. an `APPROVED` run whose period is still `CLOSED` because the event sits in the DLT). (7) Payroll-without-T&A tenants: the attendance import produces a `CLOSED` result version, so the same protocol applies (GAP-060).

### 7.2 Monthly sequence (example: cut-off 25th, pay date 5th; D = period end)

| Step | When | Actor | Action | State change / event |
|---|---|---|---|---|
| 1 | Before period | Payroll | Publish the pay calendar: attendance cut-off, optional OT cut-off, **T&A close deadline (D + 2 WD)**, approval deadline (D + 5 WD), pay date, std-day method | `pay.PayCalendarPublished`; T&A creates period `OPEN` |
| 2 | During period | People / T&A / Payroll | People changes flow as effective-dated events; T&A processes punches and requests; Payroll may run `PROVISIONAL` simulations | — |
| 3 | D + 1, 00:00 | T&A (scheduler) | Period moves to review. Requests for the period are still accepted; the exception dashboard starts (BR-ATT-074) | `OPEN → IN_REVIEW` |
| 4 | D + 1 … D + 2 WD | Managers, T&A admin | Clear exceptions; optional manager/employee sign-off; **close** per LE × pay group | `IN_REVIEW → CLOSED`; `att.AttendancePeriodClosed(v1)` |
| 5 | D + 2 … D + 3 WD | Payroll admin | Set `INPUT_CUTOFF`: the snapshot records the People event watermark and the Attendance Result version(s). Run `FINAL` calculation and fix exceptions | Run `CALCULATED`; `pay.PayrollRunStatusChanged(CALCULATED)` |
| 6 | Before submit (no hold yet) | T&A admin | If re-open is needed: `CLOSED → OPEN` with reason. Payroll marks the run **stale** and blocks submit until it is recalculated on the new version | `att.AttendancePeriodReopened`; re-close → `att.AttendancePeriodClosed(v2)` |
| 7 | Any time before approval | People | A People event whose effective date is ≤ period end and arrives after the watermark sets the flag "input changed since calculation". The admin either recalculates (withdrawing the run to `CALCULATED` if it is submitted, step 10) or explicitly defers it to retro (logged) | — |
| 8 | D + 3 … D + 4 WD | Payroll admin | **Submit** the run. For each in-scope period Payroll calls `acquireHold(period, vN, runId)` (sync, idempotent). T&A grants it only if the period is `CLOSED` and vN is current. Any refusal → the submit fails and the run stays `CALCULATED` | Hold `ACTIVE`; `att.AttendancePeriodHoldGranted`; run `CALCULATED → SUBMITTED` |
| 9 | While `SUBMITTED` | T&A admin → Payroll admin | T&A needs to re-open a **held** period: T&A refuses the direct re-open and raises a release-request task to the payroll admin (BR-ATT-087). Payroll releases the hold; the run returns to `CALCULATED` with the stale flag; the re-open then proceeds as in step 6 | `att.AttendancePeriodHoldReleased(REOPEN_REQUESTED)`; run `SUBMITTED → CALCULATED` (stale) |
| 10 | While `SUBMITTED` | Approvers / Payroll admin | **Rejection** (→ `DRAFT`), **withdrawal** by the admin (→ `CALCULATED`) or cancellation: Payroll releases the hold. Re-submit returns to step 8 | `att.AttendancePeriodHoldReleased(REJECTED / WITHDRAWN / CANCELLED)`; `pay.PayrollRunStatusChanged(REJECTED)` |
| 11 | D + 4 … D + 5 WD | Approvers (Core workflow) | **Approve.** Gate: every in-scope period is `CLOSED` with an `ACTIVE` hold of this run on the current version; no stale or unresolved "input changed" flag | Run `SUBMITTED → APPROVED`; `pay.PayrollRunStatusChanged(APPROVED, versions consumed)` |
| 12 | On `APPROVED` | T&A | Lock the held version. The version is guaranteed by the hold, so the lock cannot fail; a detected mismatch is a reconciliation incident, never an approval rollback | `CLOSED → LOCKED`; hold `CONSUMED`; `att.AttendancePeriodLocked` |
| 13 | After `APPROVED` | Payroll | Bank file, GL, SI/TU/PIT payables; payslips released at publish time | — |
| 14 | Pay date + bank confirmation | Payroll | Mark paid; close the period when outputs are complete (BR-PAY-080) | `APPROVED → PAID → CLOSED`; pay period `CLOSED` |
| 15 | After `LOCKED` | T&A | Any change touching the period (late correction, leave cancel, holiday change) → delta lines in the **next OPEN period's** result, or an **off-cycle result** for leavers with no open period | `att.RetroDeltaCreated` |
| 16 | After `APPROVED` | Payroll | Back-dated People changes (salary, dependants, assignment) are detected from effective dates → retro components in the next open run (BR-PAY-076). People marks `retro=true` for information only | — |
| 17 | Exceptional | Payroll (privileged + second approval) | **Unlock** of an approved run → T&A `LOCKED → CLOSED` with the same version (the only reverse path for a locked period) and the hold is released; return to step 5. **Reversal** of a paid run leaves T&A untouched and corrects via off-cycle/retro | Run `UNLOCKED → DRAFT`; `att.AttendancePeriodClosed(cause UNLOCK)`; `att.AttendancePeriodHoldReleased(UNLOCKED)` / run `REVERSED` |
| 18 | Back-dated Core change | Core | A reorg or LE attribute change crossing an `APPROVED` period needs `CORE_REORG_BACKDATE`; Core reads the LE lock state from the runs of all its pay groups (GAP-049) | — |
| 19 | Nightly | SaaS scheduler → Payroll | Reconciliation of run, hold and period states for all tenants; alert on mismatch | Business monitor (architecture §14.5) |

### 7.3 Leaver sub-sequence (resolves GAP-070)

1. `people.TerminationScheduled` (LWD, termination date, access-revocation date). T&A blocks leave after LWD and projects the balance. Payroll opens a `final_settlement` and starts the deadline clock from the termination date (owner Payroll, GAP-040). Core schedules the user downgrade.
2. LWD: T&A individual early close → `att.LeaverAttendanceClosed` (final result version, encash/recover days).
3. Termination date: `people.EmployeeTerminated` (eligibility, periods, deductions, assets outstanding). Core switches the user to `FORMER_EMPLOYEE`.
4. Payroll runs the **final-settlement off-cycle run** (Attendance Result + People inputs + loans + SI history) → submit (holds the leaver's individual result version, as in §7.2 step 8 — v1.1) → approval (T&A locks that version) → payment → `pay.FinalSettlementStatusChanged`. Then the D02-LT decrease.
5. People closes the separation case, generates the documents and issues the PIT certificate request. Any later T&A delta for the leaver → off-cycle result → correction run.
